# Градиент моделей в объединённом приключении

`scripts/gradient_codex_calibration.py` использует существующий парный исполнитель
в отдельном процессе и приватном каталоге; он не меняет и не возобновляет
предыдущие прогоны. Вместе сравниваются GPT‑6 Luna, GPT‑6.2 Sol и GPT‑6.2 Astra:
для каждой модели один и тот же мир внутри каждой тройки, одинаковые настройки
`reasoning_effort=low`, инструкция, окно истории, условия игры и лимиты. Различие
уровней моделей не гарантирует монотонность результата на одной выборке.

```sh
python3 scripts/gradient_codex_calibration.py init gradient-dev \
  --memory medium --navigation easy --quests hard --combat off --party off \
  --dev-worlds 1 --holdout-worlds 3 --max-turns 200 \
  --max-actions 80 --context-turns 80 --max-calls 260 --max-input-tokens 7000000
python3 scripts/gradient_codex_calibration.py run gradient-dev --split dev
python3 scripts/gradient_codex_calibration.py status gradient-dev
# После выбора и фиксации модели эксперимента и получения полной dev-тройки:
python3 scripts/gradient_codex_calibration.py seal gradient-dev
python3 scripts/gradient_codex_calibration.py run gradient-dev --split holdout
```

Одно исследовательское условие не доказывает статистически надёжного градиента.
Разные планы получают разные приватные миры: они не являются парными по уровням.
Чтобы раздельно оценивать оси, изменяйте одну настройку при фиксированных
остальных, отдельно учитывая возможное изменение мира; новая конфигурация требует
нового плана. Бои и партия включаются через `--combat` и `--party`.

Статус показывает **исход и диагностический score 0–100 отдельно**. Score
[radical-score-0.1.0](radical-score.md) выдаёт частичный прогресс по обязательным
этапам, обоснованным посещениям целей, коду, бою и финалу; исходная победа
остаётся отдельной метрикой. Для выключенного боя вес перенормируется. Показывать
средний score только как описательную статистику завершившихся игровых исходов,
всегда вместе с числом запланированных и завершённых партий. Не сравнивать
score разных конфигураций с различающимся набором компонентов или весов.
Ни техническую ошибку, ни лимит исполнителя нельзя превращать в нулевой score:
они отображаются как незавершённые с `null`. Игровой `turn_limit`, напротив,
является терминальным исходом по правилам среды и получает частичный score.
Результаты и разложение компонентов печатаются без скрытого seed.

Доступ к holdout открывается только после `seal` и полной dev-тройки. История
содержит лишь наблюдения и канонические действия, сохраняя одноразовую подсказку.
Блокируется повтор неопределённого вызова. Отпечаток кода включает скорер,
сценарий, транзитивные зависимости и все три runner; полная версия и аргументы
CLI также фиксируются. Записи о ходе и приватные сиды находятся под
`~/.local/share/adndbench/gradient-codex-calibrations/` с правами владельца.

На каждый ход создаётся отдельная Codex-сессия, инструментальные вызовы
проверяются по событиям, но полной изоляции файлов нет. Ограничители количества
запросов, токенов и времени действуют отдельно для каждого split; токенный
лимит проверяется между запросами, так что один запрос может превысить порог.
Он не является денежным лимитом. Сравнение трёх моделей умножает число запросов
по сравнению с одной. `init`, `seal`, `status` — без вызовов моделей.
Остальные детали и ограничения — в [инструкции](paired-radical-adventure.md).

Проверка без модели: `python3 -m unittest scripts.test_gradient_codex_calibration -v`.

## Компактная история

Для этой серии зафиксирован отдельный protocol
`deduplicated-stable-fields-0.1.0`: в **предыдущих** наблюдениях опускаются
только подряд повторённые значения `tasks`, `scouting` и `combat_rules`, если
они совпадают с полным текущим наблюдением. Первое появление и каждое изменение
этих полей сохраняются; уникальные сведения, действия, сообщения, подсказки,
состояния инвентаря, партия, бой и все остальные поля не удаляются. Текущее
наблюдение передаётся целиком. Модель явно получает описание этого формата.
Это отдельный prompt protocol; результаты нельзя автоматически объединять с
сериями, где вся история подавалась без сокращения. Он и его исходный код входят
в зафиксированный отпечаток плана.

На одном локальном примере 20 исторических ходов объём JSON-истории сократился
примерно на 82–83% в байтах (с боем и без). Это проверка конкретного примера,
а не гарантия такого же сокращения числа токенов или стоимости. Тесты сверяют
полноту текущего наблюдения, сохранность действий и уникальных подсказок,
первых появлений и изменений, а также отсутствие побочных изменений истории.
